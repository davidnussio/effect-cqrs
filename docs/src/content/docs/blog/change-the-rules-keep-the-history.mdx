<Image src={cover} alt="A librarian on a ladder hangs a new rules board next to the old one, while at the desk below a colleague stamps a new card in a different colour beside a row of cards stamped before" />

Every summer the library relaxes its rules: five books instead of three, four weeks instead of
three. On the first of September the old rules come back. In the CRUD version of the library,
the loan period is a setting, and due dates are worked out when they are shown:

```sql
SELECT title, lent_on + (SELECT loan_days FROM settings) * interval '1 day' AS due_on
FROM loans WHERE returned = false;
```

On September 1st someone changes `loan_days` from 28 to 21. Every loan made in August is now
a week shorter, and the reminder job emails a few hundred members that their books are
overdue. They were told four weeks, and they were right.

Business rules change: prices, limits, periods, fees, eligibility. This post shows where they
belong in an event-sourced system so that a change applies to new decisions and leaves the old
ones alone. Every snippet runs in
[`examples/blog/change-the-rules.test.ts`](https://github.com/davidnussio/effect-cqrs/blob/main/examples/blog/change-the-rules.test.ts),
which moves the clock from August to September.

## Never check rules in a projection

Look at the projection again: it checks nothing. A member with four books when the limit is
three is a state it folds without complaint. That is on purpose.

A projection runs on every load, over every event ever recorded, with today's code. If it
checked today's limit, Alice's stream would fail to load the moment the rules changed, and
she could neither borrow nor return a book. Worse, the projection would be judging decisions
made under rules it doesn't know about. Events are what happened. A projection that disagrees
with them is wrong, not the events.

So rules go in command handlers, where they decide about the future, and projections only
record what was decided.

<Aside>
The same goes for read models. A report of "members over the limit" in September lists Alice,
correctly: she has four books and the limit is three. Whether that is a problem is a question
for the report, which can say she got them under the summer rules, because the events say so.
</Aside>

## Facts and conclusions

[Fix the code, not the data](../fix-the-code-not-the-data/) recommended working out conclusions
in read models, so that a replay can fix them. This post stores the due date in the event.
Both hold, because they are different things:

- **A decision someone was told is a fact.** The due date on Alice's slip, the price on an
  invoice, the fee in a confirmation email. Store it in the event, with what decided it.
- **A judgment you may revise is a conclusion.** Whether a member is a frequent borrower,
  which books are popular, whether a return was late by a newer definition. Work it out in a
  read model, from the facts.

If you are unsure which one you have, ask whether a customer would be upset if it changed
after the fact. If yes, it is a fact.

## Rules of thumb

- **Rules run in command handlers, on the day of the decision.** Never in projections.
- **Store the outcome, not the inputs and a formula.** `dueOn`, not `lentOn` plus a setting.
- **Record which rule decided.** A name or a version in the event answers "why" for years.
- **Keep old rules around with their dates.** They explain the history, and a rule that takes
  effect later is deployed before its date like any other entry.
- **Load whatever the log says.** A state that today's rules wouldn't allow is a state that
  older rules did.
