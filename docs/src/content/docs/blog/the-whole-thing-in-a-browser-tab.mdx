Alice has €10 in her account and clicks "withdraw €200". Where does the page say no?

In most front ends the answer is "wherever someone remembered to": an `if` in the click
handler, a disabled button, a check inside a reducer that then has to return the old state
and report the problem some other way. If you have used Redux you know the shape: an action
is a fact, and a reducer can't refuse it. By the time it runs, the action has happened.

Then comes the transfer, which takes money from one account and gives it to another, and
must give it back when the second account turns out to be closed. That is a process with
steps, a failure and an undo. redux-saga was built for exactly this, and it had the right
idea. Many teams that adopted it still ended up with generator functions nobody wanted to
touch six months later, because the effects they yielded had no types and the rules they
depended on lived somewhere else.

Redux is already half of event sourcing: actions are events, and reducers fold them into
state. The other half has names for what was missing. A *command* is a request that can be
refused, and a *saga* is a process across several things, with typed failures.
effect-cqrs is written for servers, but nothing
in it needs one. The <a href={demoUrl}>bank demo</a> runs the whole framework in a tab, with
React on top, and this post walks through the code that joins the two. Every snippet is
quoted from the demo's source, in
<a href={sourceUrl("examples/bank-ui/src")}><code>examples/bank-ui</code></a>.

## A command that can say no

An account is an aggregate. Its state is folded from its events, and each command is a
function that reads that state and either returns events or fails. These are the two
commands of a transfer:

`sendTransfer` has three ways to refuse, and each is a class with fields:
`InsufficientFunds` carries the balance and the amount asked for. When the handler fails,
no event is stored and nothing changes. There is no old state to hand back, because the
state was never touched.

Nothing in this file knows about the browser. It imports `effect` and `effect-cqrs`, and it
is the same file you would put behind an HTTP API with PostgreSQL under it.

## Sending a command from a component

The service has one typed function per command. The demo wraps them in one function that
returns a promise:

<Code code={region(engine, "command")} lang="ts" title={engineFile} />

Two things about its type. The command's name picks the payload, so
`engine.command("withdraw", id, { amout: 50 })` doesn't compile, and neither does a command
that doesn't exist. And the promise never rejects for a refusal: `Effect.result` turns the
failure into a value, a `Result` with the errors that command can fail with.

## Reading

Components don't read aggregates. They read *view models*, which follow the log and keep
data in the shape a screen needs. The one behind the account cards keeps a row per account:

`devstore` is a plain object with `get`, `subscribe` and a few functions that replace its

The view model runs after the command, not inside it, so for a moment the card shows the
old balance. In the demo you can stretch that moment with a slider and watch the read side
trail the log. It is the same lag a server has between its log and its tables, and seeing
it in a page makes it easier to design for.

## A process across two accounts

A transfer touches two aggregates, and a command touches one. `sendTransfer` only takes the
money out and records `TransferSent`. A saga does the rest:

<Code code={region(engine, "saga")} lang="ts" title={engineFile} />

Read the workflow top to bottom: credit the other account, and if that is refused because
the account isn't open, refund the sender. The failure it handles is the typed error from
the aggregate, caught by its tag. The transfer's id is the idempotency key, so starting the
same transfer twice joins the run under way, and `receiveTransfer` ignores an id it has
already seen.

This is the part front ends usually get wrong, because it is spread over a click handler,
two requests and a `catch`. Here it is one function that says what the process is.

## What this is not

It is a demo of how little joins the two, and it stops where the hard part starts.

- **The store lives as long as the page.** Reload and the bank is gone. The demo uses the
  in-memory event store on purpose.
- **Nothing is synchronised with a server.** Running the same aggregate on both sides, so
  the page can refuse a command at once and the server has the last word, is the
  interesting next step. It needs an answer for what happens when they disagree, and this
  post doesn't have one.
- **There is no package of hooks.** `engine.command` and `useSnapshot` are about twenty
  lines in the demo, written for one aggregate. Whether they deserve a library depends on
  whether anyone wants one.

## Rules of thumb

- **Put the rule where it can refuse.** A command handler decides before anything is
  stored, so there is nothing to undo.
- **Return a refusal, don't throw it.** A `Result` with typed errors lets the component
  `switch` on the tag and read the fields.
- **Let components read view models.** One store, one `useSyncExternalStore`, and the read
  side is done.
- **Write a process as one function.** A saga with its failure and its undo in one place is
  easier to read than the same steps spread over handlers.
