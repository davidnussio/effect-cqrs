The demo is the classic event sourcing example, a bank, built on the framework as it is:
the same sources the tests run, bundled for the browser. Bank accounts are aggregates,
three view models project them, and a saga moves money between accounts.

At the top, a customer app renders only the read models, so their lag behind the event
store is visible, and beside it the live pipeline shows each command on its way through the
bus. Below them the page follows a command through the framework, a section at a time: slow
each stage down, read the log, crash a projection, and travel back through the history.

To run it locally:

```bash
pnpm ui
```

The code quoted below comes from the demo's sources when this site is built, so it can't
drift from what runs.

## The account aggregate

An account's balance is never stored. It is folded from the money that went in and out,
so the events are the whole truth:

<Code code={region(account, "events")} lang="ts" title={accountFile} />

The aggregate folds them into a state with a status, an owner and a balance, and its
commands check that state before they decide:

<Code code={region(account, "aggregate")} lang="ts" title={accountFile} />

A command that would break a rule, such as withdrawing more than the balance, fails with a
typed error and stores nothing. The customer app shows those rejections as they happen.

## Transfers, between two aggregates

A command changes one aggregate, and a transfer touches two. So it is split in two:
`sendTransfer` debits the sender, and `receiveTransfer` credits the receiver once it hears
about it.

<Code code={region(account, "transfer")} lang="ts" title={accountFile} />

`receiveTransfer` records the transfers it has credited. If it runs twice for the same
transfer, the second time decides on nothing, so the saga below can safely retry.

The [saga](../../guides/sagas/) starts a workflow for each `TransferSent` event. The
workflow sends `receiveTransfer` to the other account, and when that is refused, because
the account is closed for instance, it refunds the sender. Each command is an activity, so
the engine keeps its outcome:

<Code code={region(engine, "saga")} lang="ts" title={engineFile} />

Between the two steps the money is in flight. The bank vault, a view model, shows that
amount.

## Three view models

Each view model folds the same events into a different shape, keeps its own checkpoint, and
can be thrown away and rebuilt:

- **accounts**: one row per account, with its balance, for the customer app.
- **bank-totals**: money in the bank, money in flight, and counts by event type.
- **activity-feed**: the latest 40 events, as sentences.

Their storage is a plain object outside React and Effect, so the screen shows exactly what
they hold. Delivery is at least once, so the accounts view ignores an event whose position
it has already applied:

<Code code={region(views, "accounts-view")} lang="ts" title={viewsFile} />

`bank-totals` has a switch in the **Projections** section that makes its handler fail. Turn it on and the
view model stalls on that event and retries with backoff, while the other two carry on.
Turn it off and it catches up, without skipping anything.

## Wiring it together

The whole engine is a layer: the in-memory store, checkpoints and snapshots, the service,
the view models, and the background fibers that mirror events to the devtools, run the
saga, poll the view models' status and the service's metrics, and send random traffic. The
service keeps only four accounts in memory and saves a snapshot every five events, so with
more accounts open the **Trace & metrics** section shows commands starting from snapshots and replays.

<Code code={region(engine, "wiring")} lang="ts" title={engineFile} />

A `ManagedRuntime` runs it, and React reaches it through plain functions. **Reset**
disposes the runtime and starts a new one.

## Forgetting an owner

The owner's name is [personal data](../../guides/personal-data/): `AccountOpened` stores it
encrypted with a key of the account's own, which the **Event store** section shows as a
`$personal` block. **forget** on a card destroys that key:

<Code code={region(engine, "forget")} lang="ts" title={engineFile} />

The log doesn't change and the totals still add up, while the card, the feed and every
replay read `[forgotten]`. The accounts view erases the name in `onForget`, and new
commands on the account still work, since deposits hold no personal data.

## The devtools

Everything is on one page, in the order a command goes through the framework, and the
header links to each section.

| Section | What you can do |
| --- | --- |
| Bank | Send commands from the cards, and watch each one go through validating, loading, deciding and appending in the live pipeline beside them. Pause the bus and step it, or turn the autopilot on |
| Commands | Slow the stages and the projections down, and send raw JSON to `dispatch` |
| Event store | Read the log as it grows |
| Projections | See each view model's checkpoint and lag, crash `bank-totals`, and rebuild one |
| Time travel | Scrub through the log: the customer app becomes a preview, where each account is its events up to the cursor folded with the aggregate's projection. Replay view models up to a chosen event, or entirely |
| Trace & metrics | Follow every span Effect opens, recorded by a `Tracer` of the demo's own: each command on the bus with the stages it waited in, the aggregate's span and `EventStore.append`, and for a transfer the saga's workflow and its activities. Beside the trace, watch the service's [metrics](../../guides/commands/#metrics): where each load found its state, the events it read, the states in memory and those dropped, the snapshots saved, and how long each command took by outcome |

<Aside>
Replaying up to an event uses the `finishTime` of `viewModels.replay`, since the replay
API takes a time window rather than a position.
</Aside>
